## ARCHITECTURE COMPONENTS

### **Wave 1: Foundation Infrastructure** ✓ BUILT

**1. MessageIDGenerator** (`message_id_generator.py`)
- Generates unique, sortable message IDs
- Format: `MSG-{YYYYMMDDHHMMSSMMMM}-{8-HEX}`
- Example: `MSG-20260621093045123-A7F2E8CD`
- Status: **WORKING** (tested with your Telegram message)

**2. DeliveryLedger** (`delivery_ledger.py`)
- JSONL append-only audit trail
- Events logged:
  - `delivery` - message sent
  - `response` - user replied
  - `engagement_window_closed` - no reply within 1 hour
- Methods:
  - `log_delivery()` - log send event
  - `log_response()` - log user reply
  - `log_no_response()` - log window closed
  - `get_deliveries_for_persona()` - query deliveries
  - `get_responses_for_message()` - query responses
- Status: **WORKING** (tested with your delivery)

**3. TelegramRelayClient** (`telegram_relay_client.py`)
- Abstraction layer for Hermes relay
- Methods:
  - `send_message(chat_id, text)` - send message via Telegram
  - `get_updates(offset, timeout)` - poll for new messages/replies
  - `check_reply_to_message_id(update)` - extract reply correlation ID
- Status: **WORKING** (sent real message to your account)

### **Wave 2: Orchestration & Response Monitoring** ✓ BUILT

**4. DeliveryOrchestrator** (`delivery_orchestrator.py`)
- Coordinates complete delivery lifecycle:
  1. Generate unique message ID
  2. Log "pending" status before send (crash safety)
  3. Send via TelegramRelayClient
  4. Log "success" or "failure" status
  5. Spawn ResponseMonitor thread on success
- Methods:
  - `deliver(persona, message_text, intent, chat_id, context_tags)` → DeliveryResult
- Return type: `DeliveryResult(status, message_id, telegram_message_id, error)`
- Status: **BUILT** (ready for integration)

**5. ResponseMonitor** (`response_monitor.py`)
- Background daemon threads for polling replies
- Architecture:
  - One daemon thread per message (non-blocking)
  - Polls `get_updates()` every 30 seconds
  - Correlates replies via `reply_to_message_id == telegram_message_id`
  - Logs response with `engagement_latency_seconds`
  - Enforces 1-hour engagement window deadline
  - Clean shutdown with main process (daemon threads)
  
- Methods:
  - `__init__(telegram_token, ledger_path, default_window_seconds=3600)`
  - `monitor(message_id, telegram_message_id, persona, sent_at, window_seconds=None)`
  - `_monitor_loop(...)` - background polling thread
  
- Error Handling:
  - `GatewayPollingConflict`: 60s backoff, retry (no crash)
  - Network errors: 30s backoff, retry
  - ALL exceptions caught: threads never crash
  
- Status: **FULLY BUILT** (extensive implementation)

### Step 3: User Replies (Telegram)

User taps "Reply" to AMMAR's message in Telegram:

```
User replies: "Will do"
```

### Step 4: Response Detection (Background Thread)

ResponseMonitor thread polls `get_updates()` every 30 seconds:

```
Polling cycle 1 (00:31): No updates
Polling cycle 2 (00:32): No updates
...
Polling cycle 5 (00:34:15): FOUND REPLY!
  - update contains reply_to_message_id = 12345
  - matches our telegram_message_id = 12345
  - Extract response text: "Will do"
  - Calculate latency: 150 seconds
  - Log to ledger: log_response()
  - Thread exits (response found)
```

### Step 5: Response Logged

```python
ledger.log_response(
    message_id="MSG-20260621003045123-A7F2E8CD",
    telegram_message_id=12345,
    response_text="Will do",
    response_time="2026-06-21T00:32:15Z",
    engagement_latency_seconds=150,
    persona="AMMAR"
)
# Entry appended to DELIVERY_LEDGER.jsonl
```

### Alternative: No Reply (Engagement Window Closes)

If user doesn't reply within 1 hour:

```
Polling continues until 01:30:45 UTC (1 hour deadline)
At 01:30:45: deadline exceeded
  - Log to ledger: log_no_response()
  - Thread exits (window closed)
```

```python
ledger.log_no_response(
    message_id="MSG-20260621003045123-A7F2E8CD",
    telegram_message_id=12345,
    persona="AMMAR"
)
# Entry: {"event_type": "engagement_window_closed", ...}
```
