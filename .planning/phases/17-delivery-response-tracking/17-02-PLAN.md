<objective>
Build the active delivery and monitoring infrastructure for Phase 17: delivery orchestrator that coordinates message sending with unique ID assignment and ledger logging, plus response monitor that polls Telegram for user responses within the 1-hour engagement window. Together with Wave 1, satisfy all five DELIVERY requirements for twice-daily Telegram nudges with response tracking.

**Purpose:** Implement the critical path for message delivery (orchestrator) and response capture (monitor). DeliveryOrchestrator coordinates the full delivery lifecycle; ResponseMonitor maintains background threads for engagement tracking.

**Output:**
- DeliveryOrchestrator: deliver() method that orchestrates ID generation → relay send → ledger log → monitor spawn
- ResponseMonitor: monitor() method that spawns background thread, _monitor_loop() that polls relay and logs responses
- Integration of Wave 1 components (MessageIDGenerator, DeliveryLedger, TelegramRelayClient)
- Updated public API to export both classes
- Test suite validating delivery flow, response correlation, 1-hour window behavior
</objective>

     - Store token, ledger_path, monitor_window_seconds

   - `deliver(persona: str, message_text: str, intent: str, chat_id: int, context_tags: list[str]) -> DeliveryResult`
     - **Step 1: Generate message_id**
       - msg_id = MessageIDGenerator.generate()
       - sent_at = datetime.now(timezone.utc).isoformat()
     
     - **Step 2: Log pre-send entry** (fail-safe: message tracked before relay call)
       - ledger.log_delivery(message_id=msg_id, telegram_message_id=None, persona=persona, message_text=message_text, intent=intent, sent_at=sent_at, delivered_at=None, context_tags=context_tags, status="pending")
     
     - **Step 3: Send via relay** (try/except on all exceptions)
       - response = relay_client.send_message(chat_id, message_text)
       - tg_message_id = response.get("result", {}).get("message_id")
       - delivered_at = datetime.now(timezone.utc).isoformat()
     
     - **Step 4: Update ledger on success**
       - ledger.log_delivery(message_id=msg_id, telegram_message_id=tg_message_id, persona=persona, message_text=message_text, intent=intent, sent_at=sent_at, delivered_at=delivered_at, context_tags=context_tags, status="success")
     
     - **Step 5: Spawn response monitor** (if response_monitor is set)
       - response_monitor.monitor(message_id=msg_id, telegram_message_id=tg_message_id, persona=persona, sent_at=sent_at, window_seconds=monitor_window_seconds)
     
     - **Step 6: Return success result**
       - return DeliveryResult(message_id=msg_id, telegram_message_id=tg_message_id, sent_at=sent_at, delivered_at=delivered_at, status="success", error=None)
   
   - **On exception (catch all):**
     - delivered_at = None
     - error_msg = str(exc)
     - ledger.log_delivery(..., status="failure", error_reason=error_msg)
     - return DeliveryResult(message_id=msg_id, telegram_message_id=None, sent_at=sent_at, delivered_at=None, status="failure", error=error_msg)

Create HIKMAH__knowledge_index/delivery/response_monitor.py module implementing ResponseMonitor class:

1. **ResponseMonitor class** with __init__, monitor(), and _monitor_loop():
   - `__init__(telegram_token: str, ledger_path: Path, relay_client: Optional[TelegramRelayClient] = None, default_window_seconds: int = 3600)`
     - Store token, ledger_path, default_window_seconds
     - Initialize DeliveryLedger(ledger_path)
     - Initialize TelegramRelayClient(token) or use provided relay_client
     - Initialize _monitors dict {} to track active monitor threads
     - Initialize _offsets dict {} to track getUpdates offset per monitor (prevent duplicate updates)
     - Initialize _global_offset = 0 (shared offset for all monitors)
   
   - `monitor(message_id: str, telegram_message_id: int, persona: str, sent_at: str, window_seconds: Optional[int] = None) -> None`
     - Calculate deadline: sent_dt = datetime.fromisoformat(sent_at) → deadline = sent_dt + timedelta(seconds=window_seconds or self.default_window)
     - Spawn daemon thread calling _monitor_loop() with args (message_id, telegram_message_id, persona, sent_at, deadline)
     - Store thread in _monitors[message_id] for potential cleanup
     - Docstring: Non-blocking, spawns background thread
   
   - `_monitor_loop(message_id: str, telegram_message_id: int, persona: str, sent_at: str, deadline: datetime) -> None`
     - Poll interval: 30 seconds (configurable constant at module level)
     - Loop: `while datetime.now(timezone.utc) < deadline:`
       - Try:
         - Call relay_client.get_updates(offset=self._global_offset, timeout=25)
         - For each update in updates:
           - reply_to_id = relay_client.check_reply_to_message_id(update)
           - If reply_to_id == telegram_message_id:
             - Extract response_text from update.get("message", {}).get("text", "")
             - response_time = datetime.now(timezone.utc).isoformat()
             - engagement_latency = (response_dt - sent_dt).total_seconds()
             - ledger.log_response(message_id=message_id, telegram_message_id=telegram_message_id, response_text=response_text, response_time=response_time, engagement_latency_seconds=engagement_latency, persona=persona)
             - Return (exit monitor loop, response found)
           - Else:
             - Continue (this reply is for a different message)
         - Update self._global_offset to highest update_id + 1 (prevent replaying updates)
       - Except GatewayPollingConflict:
         - Log warning (another process owns polling)
         - Sleep and retry (backoff: wait 60 seconds before next attempt)
       - Except other exceptions:
         - Log warning (network error, etc.)
         - Sleep and retry
       - Sleep poll_interval before next iteration
     
     - After deadline (loop exits):
       - ledger.log_no_response(message_id=message_id, telegram_message_id=telegram_message_id, persona=persona)
       - Clean up: del self._monitors[message_id]

2. **Module docstring** (80+ lines):
   - Purpose: Background monitoring of 1-hour engagement window
   - Why daemon threads: Exit when main process exits, prevent zombies
   - Polling strategy: 30-second intervals (balance between latency and resource usage)
   - Response correlation: Exact match via reply_to_message_id (Telegram native field)
   - Offset tracking: Prevents update replay (maintains _global_offset across all monitors)
   - Error handling: GatewayPollingConflict (another poller owns channel), network errors (retry with backoff)
   - Cleanup: Window close logged, threads removed from tracking dict

3. **Constants at module level:**
   - POLL_INTERVAL_SECONDS = 30
   - POLLING_CONFLICT_BACKOFF_SECONDS = 60

4. **Imports:**
   ```python

   import time
   import threading
   from pathlib import Path
   from typing import Optional

   ```

5. **Error handling:**
   - GatewayPollingConflict: Log, backoff 60s, retry (don't crash)
   - Network errors: Log, sleep poll_interval, retry
   - All exceptions caught in _monitor_loop (never propagate to raise)
   - Deadline exceeded: Log no_response, exit gracefully

6. **Threading safety:**
   - Use threading.Lock if concurrent access to _global_offset (for thread-safe offset updates)
   - Or: Use lock-free approach if each monitor uses same offset (simpler, acceptable for this use case)
   - Document concurrency model in docstring
